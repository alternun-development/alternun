# Partner Admin Identity: Codebase Impact Analysis

## Scope and discovery method

This analysis covers an invitation-only partner administration model behind
`admin.alternun.co/login`, with Authentik hosted at `login.alternun.co` and
used as the sole credential, MFA, recovery, session, and identity authority.
Supabase remains an application-data projection keyed by the Authentik
principal; it must not become a second password authority.

Code discovery used the ready `codebase-memory-mcp` index for
`/home/ed/Documents/Alternun/alternun` (`search_code`, `search_graph`, and
`get_code_snippet`), then narrow source reads for configuration and generated
template boundaries. No application or infrastructure code was modified.

## Dependency and rollout order

1. Approve authorization matrix and partner organization ownership model; enumerate the exact admin resources and destructive actions. No code can safely decide tenant boundaries by inference.
2. Add database principal, organization, membership, audit, and soft-delete schema; then implement API-side strict authentication, permission, and scope enforcement with tests. Do not invite external partners beforehand.
3. Build the BFF/session model and adapt the admin SPA to same-origin cookie requests. Deploy it alongside server enforcement before switching live users.
4. Extend the idempotent Authentik bootstrap: groups/claims, invite-only local credentials, branded UI, recovery, mandatory MFA, and step-up policy. Add partner users only through invitations.
5. Provision `login.alternun.co`, certificate, DNS, issuer/client config, Authentik branding, and external-provider callback settings. Run controlled issuer migration/re-authentication.
6. Harden and reconcile Authentik-to-Supabase projection. Backfill only from Authentik and retain stable `(iss, sub)` mappings.
7. Pilot with a dedicated test partner organization and read-only role; test provisioning, revocation, cross-tenant denial, delete protection, logging, and recovery before production rollout.

## Key risks and decisions for the full task specification

- **Issuer migration:** changing `sso.alternun.co` to `login.alternun.co` changes OIDC issuer strings and the `(sub, iss)` uniqueness key. Existing projections need a deliberate migration/reconciliation; treating domains as interchangeable will create duplicate principals.
- **Public OIDC client:** the current provider is deliberately `public` because the SPA cannot protect a client secret. A BFF can use confidential-client features, but this requires exact callback/session design—not simply adding a secret to Vite.
- **Webhook integrity:** accepting a lifecycle webhook while its secret is unset makes account projection remotely writable. This must be fixed before depending on webhooks for partner access.
- **Role semantics:** current bootstrap maps every allowed group to `platform_admin`. It cannot represent read-only or scoped partner roles and would overprivilege a new `@alternun.io`/team group.
- **Tenant isolation:** role alone is insufficient. Every list, lookup, mutation, export, and background operation must filter/authorize partner organization scope on the server.
- **No automatic domain enrollment for partners:** `@alternun.io` may receive a separate internal read-only rule later, but external allies remain explicit invitation-only identities.
- **MFA and recovery:** enforce MFA before administrative access, ideally WebAuthn/passkeys with TOTP recovery. Do not make mailbox possession the sole factor for a privileged user-data console.
- **Operational authority:** production Authentik user/group assignment, DNS changes, OAuth provider callback change, and secret rotation require approved production access. Repository work can prepare and validate, but must not attempt unapproved deployment.

## Verification plan

### Unit and integration tests

- Extend `apps/admin/test/auth-build-startup.test.mjs` for the new login entry, absence of localStorage token persistence, safe redirect behavior, and read-only UI restrictions. Add component/unit tests for access-control display decisions if the current source-regex test style is retained.
- Add API tests under `apps/api/test/` for exact issuer/JWKS/audience validation, expired and malformed tokens, missing claims, denied role, permitted role, cross-organization list/get/update/delete denial, disabled membership, and recent-authentication/step-up requirements.
- Add test coverage for all mapped admin controller/service endpoints, including a direct HTTP mutation test proving that a read-only UI user receives `403`; do not rely on browser visibility tests.
- Add `apps/api` tests for webhook missing-secret rejection, valid secret, invalid secret, unequal-length secret, duplicate delivery idempotency, disable/delete lifecycle, and failed sync retry/reconciliation.
- Add migration tests for unique `(iss, sub)` principal projection, organization membership RLS or API guard behavior, audit event immutability, and soft-delete/restore lifecycle.
- Update `packages/infra/test/bootstrap-authentik-integrations.test.ts` to assert separate groups and least-privilege claims, invitation-only/local-password flow, username derivation, MFA bindings, brand flow, and application policy. Update `packages/infra/test/identity-pipeline-bootstrap.test.ts` and relevant deployment/environment tests for `login.alternun.co` and secret key propagation.

### End-to-end and operational checks

- In a non-production identity stage, create an invited external user and prove no username prompt, branded `login` page, password recovery, enforced MFA, access to only the permitted organization, and a read-only `403` on direct mutations.
- Verify operator and owner paths separately, including high-risk-action step-up MFA, audit event contents, soft-delete restoration, invitation expiry, role change, and immediate revocation/session invalidation.
- Validate DNS, TLS, `/.well-known/openid-configuration`, JWKS, OIDC callback/logout allowlists, CORS/CSP, secure cookie attributes, and external provider callback registration on `login.alternun.co`.
- During migration, run projection reconciliation and confirm no duplicate identities are created for the same Authentik UUID under old/new issuer values. Monitor Authentik webhook failures, BFF authentication failures, 401/403 rates, and audit-event delivery.
