# Authentik platform access (SSO admin and user interface)

Last verified: 2026-10-22 (testnet and production).

## Problem

Google/Discord login creates Authentik users with `type=external`. Authentik's
user interface (`/if/user/`) and admin interface reject external users with
"Interface can only be accessed by internal users." Only `akadmin` was ever
promoted, so `edward@alternun.io` got "Permission denied".

## What the bootstrap does now

`packages/infra/scripts/templates/bootstrap-authentik-integrations.py` promotes
users to `internal` and assigns groups on every deploy:

| Who | Groups | Stages |
| --- | --- | --- |
| `edward@alternun.io` (super admin) | `authentik Admins` | all |
| any `@alternun.io` user | `Alternun Internal Admin` | all |
| `branner@lstech.solutions` | `Alternun Internal Admin` | non-production only |
| `developers@alternun.io` (shared dev account) | `authentik Admins` | non-production only |

Configuration keys in the integration-config secret
(`alternun-infra/identity/integration-config/identity-<stage>`):
`superAdminEmails`, `internalEmailDomains`, `devAdminEmails`,
`devSharedAdminEmail`, `devSharedAdminPassword`. They are set in
`packages/infra/modules/identity-resources.ts`.

## Shared dev account

- Email `developers@alternun.io`, testnet only, never created in production.
- The password is generated by Pulumi and stored in the secret key
  `devSharedAdminPassword`. It is not in the repo. Rotate it by replacing the
  Pulumi `RandomPassword` resource.

## Verified state

- Testnet (`testnet.sso.alternun.co`): edward, branner and developers promoted
  and in the groups above; developers password set from the secret. Applied by
  running the bootstrap by hand on the instance.
- Production (`sso.alternun.co`): edward and sgomez are internal and in the
  platform/admin groups; no dev accounts exist.
- Login confirmed working by the team after these changes.

## Known issue: pipeline bootstrap warning

The `identity-dev` deploy logs "WARN: Failed to bootstrap Authentik
integrations", also on runs before these changes. SSM truncates stderr during
Authentik startup logs, so the traceback is not visible. Running the same script
by hand finishes without errors. Cause undiagnosed; likely deploy-time env or
the 300 s timeout. To debug, run on the instance:

```bash
cd /opt/alternun/identity
docker compose exec -T server sh -lc \
  '/ak-root/.venv/bin/python /manage.py shell < /templates/alternun-bootstrap-integrations.py'
```

Always validate the AWS account first
(`bash scripts/validate-aws-account.sh enforce`).
